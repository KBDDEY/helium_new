# ParallelReserveStrategy：单时段调度规则

目标是通过启动时机和占卡安排缩短本时段的 `clearance_seconds`。任务内容、图结构和执行配置保持相同。按 FIFO 每次只决定队头任务；已启动任务的卡数不再变化。

## 参数与输入

| 名称 | 定义 |
|---|---|
| `K` | 本次实际启动的 replica 总数 |
| `n` | 排队任务数，包含队头，不包含运行中的任务 |
| `F` | 当前空闲 replica 数 |
| `R` | 当前运行任务的类型集合，由调度器从 `in_flight` 生成 |
| `C(label)` | `min(config.K_MAX_TABLE[label], K)`，实际分配上限 |
| `W` | `min(config.K_WAIT_TABLE["parallel"], C("parallel"))`，实际等卡目标 |

`K_MAX_TABLE` 和 `K_WAIT_TABLE` 均由调度器作为 `plan()` 的入参传入，策略内部不固定卡数。当前表值是假设值，可在 `benchmark/repo/config.py` 修改；每次实验内保持参数不变。

`k_max` 表示再增加卡数时边际收益较低的分配上限；`k_wait` 表示值得主动积累到的卡数。两者不必相等。配置值均应为正整数。

## 按以下顺序决策

没有排队任务时清除等待状态。没有空卡时不启动任务，等待下一次完成事件。

### 1. 忙阶段：`n >= K`

队头无论哪种类型，分配一卡启动。每次启动后重新计算 `n` 和 `F`。当 `n <= K-1` 时，后续决策进入闲阶段。

### 2. 闲阶段的 iterative

始终一卡，有卡即启动。

### 3. 闲阶段的 debate

先计算队头后面的任务预算 `B`：

- 每个 parallel 按 `C("parallel")` 计入；有几个就计入几次。
- 每个 iterative 或 debate 按一卡计入。

当前 debate 分配：

```text
k = min(C("debate"), max(1, F - B))
```

预算只是本次决策的计算，不在池中实际占卡。如果 `B` 已经超过现有空卡，debate 仍单卡启动，不等待，也不跳过队头。后续每次启动后重新计算预算。

例如 `K=5、F=5、C(parallel)=3、C(debate)=3`：

- `debate → parallel`：分配 `2+3`。
- `debate → parallel → iterative`：分配 `1+3+1`。

### 4. 闲阶段的 parallel

如果该队头已经开始等卡，直接执行下面的“等卡分支”，保留它开始等待时的目标。

否则，若 `n > 1` 且 `F >= n`，空卡足够让多个排队任务各拿一张。给后面的 `n-1` 个任务各留一卡，当前 parallel 分配：

```text
k = min(C("parallel"), F - (n - 1))
```

此时允许只分一卡。例如 `K=5`、四个 parallel 排队、上限至少两卡，分配为 `2+1+1+1`。

这个分支的前提是**尚未开始等待**，即使分配少于 `W` 也立即启动，不新建等待记录。

其余情况进入等卡分支，包括只有一个排队 parallel 的情况，即使此时 `F >= n`。

### 5. 等卡分支

首次进入时使用目标 `W`。只有确实满足 `F < W`、存在非 parallel 运行任务并决定继续等待时，才记录该任务 ID 和目标；进入本分支本身不代表已经开始等待。

后续对同一队头继续使用记下的目标，不因 `F >= n` 就撤销。目标始终不超过当前 `C("parallel")`。

- `F < W` 且 `R` 中还有非 parallel：返回空分配，保留空卡，等待下一次任务完成。
- `F < W` 且没有非 parallel 在运行（包括运行中全是 parallel，或 `R` 为空）：使用当前空卡降级启动。这条同时用于首次考虑等待和已经开始的等待。
- `F >= W`：立即启动，不为超过 `W` 的卡继续等待。

启动时统一按下面的公式分配：

```text
k = min(F, C("parallel"), max(W, F - (n - 1)))
```

这表示达到目标后至少分到 `W`；超过目标的部分只使用给后续任务各留一卡后的富余卡。空卡不足时允许降级。

等待期间不跳过队头启动后续任务，因此逐张释放的卡能够积累。任务启动后清除等待状态。若队头改变或队列清空，也清除等待状态。

例如，同样是 `n=2、F=2`，没有等待记录时按普通分配给 parallel 一卡、后面留一卡；如果它之前在 `F=1` 时已经决定等两卡，则本次把两卡交给 parallel。历史状态不同导致的决策不同是规则的一部分。

## 优先级与边界

- 忙阶段始终单卡。单时段内排队数只减少，不会在一次等待期间重新进入忙阶段。
- 对 parallel，已经开始的等待优先于 `F >= n` 的普通分配规则。
- 最后一个排队 parallel 仍允许等卡。这两种情况允许推迟启动，属于有意的调度取舍。
- “给其他任务留一卡”是当前分配的预算，不能表述为所有后续任务无条件立即启动；后续队头仍会按其类型和等待状态重新决策。
- 没有运行任务可以释放卡时不继续等待；运行任务正常结束、参数有效时，策略不会自身形成永久等待。但它不能保证每个队列都比全单卡更快。

## 代码与使用

当前 `helium_new2` 默认策略仍是 `LoadAwareStrategy`；本策略显式选择：

```python
from repo.scheduler import run_experiment
from repo.strategy import ParallelReserveStrategy

report = run_experiment(strategy=ParallelReserveStrategy())
```

修改 `config.K_MAX_TABLE` 和 `config.K_WAIT_TABLE` 后重新开始实验即可；`dry_run_plan(strategy=ParallelReserveStrategy())` 也读取同一套配置。没有构造函数中写死的等卡数。

每次实验使用新的策略实例；异常中断后若要复用原实例，先调用 `reset()`。本规则只讨论单时段批量到达，不包含多时段到达后的优先级变化。
