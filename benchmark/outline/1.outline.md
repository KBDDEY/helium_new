# 多卡在线负载均衡调度：场景大纲

> 本文档记录课题场景、对照/实验设定、调度接口约定与已定策略。  
> 实现分阶段进行；策略是否有效以逻辑与实验验证为准，不要求每次数值最优。

2026-11-17 的当前方案见 [自适应调度策略讨论稿 v3（五个启发式策略）](five_strategy_design.md)。第一至第四策略在起点互斥匹配并覆盖全部非空合法队列，第五策略在全部任务启动后统一执行尾部扩卡。稿内记录参数、执行规则、证明条件与实现状态。

---

## 1. 课题目标（大面上）

在 **N 张 GPU、每卡一个常驻 vLLM 副本** 的集群上，对按 **时间段成批到达** 的 **整图单任务**（Helium / Helium_new agent 工作流）做 **负载感知的分卡调度**，缩短 **Σ execute**，并缩短各段（各波）的 **清队时间 `clearance_seconds`**。

核心矛盾：

- **可并行度**：图越宽，多卡越可能加速；
- **缓存局部性**：分卡过多会拆散共享前缀 / KV，可能变慢甚至得不偿失；
- **系统负载**：忙时多分卡往往不如多开几个单卡任务；闲时才值得按场景给单任务多卡。

课题不是「单图内如何 round-robin」，而是 **队列级：每个任务占几张卡、何时启动**。

---

## 2. 三类代表性工作负载

用现有三类 benchmark 场景作为标签（提交时 **已知**），各自代表一类任务形态：

| 标签 | 代表含义 | 分卡直觉 |
|------|----------|----------|
| **iterative** | 可并行度低（深、串行依赖） | 无论忙闲，**不宜分卡**；表上上限一般为 1 |
| **debate** | 有并行度，分卡有收益；单任务负载不算极高 | 可分卡，但分太多可能伤缓存利用率；存在「最优卡数」上限（由单场景实验测得） |
| **parallel** | 有一定并行度且负载高，分卡收益高 | 可分更多卡；最优上限通常高于 debate（由实验测得） |

后续会 **自造调度用数据集**：样本仍从 **原始数据**（如 Amazon reviews、TAT-QA 等）经现有三类工作流准备得到，只是 **预先做好**。  
**任务到达时，一条任务携带的内容已齐全**，调度侧不再现场抽样/拼提示词/构图：

| 字段 | 给谁用 |
|------|--------|
| **场景标签**（iterative / debate / parallel） | **调度系统**（决定分不分卡、上限几张等） |
| **编译好的图** | **Helium / Helium_new 运行** |
| **提示词等运行所需输入** | **Helium / Helium_new 运行** |

**如何造这套数据集尚未讨论**，实现调度前再单独定格式、规模与生成脚本。

单场景「最优分卡数」由 **独占、只跑该任务** 的墙钟实验得到，整理成 **查表**，作为调度策略的输入之一：实验组给某任务的卡数 **不超过** 表中该标签的上限。

> 说明：表反映的是「该场景自己跑」的最优 k，不是已经过系统级联合优化后的全局最优。系统级是否有效靠对照实验验证。

## 3. 硬件与运行时假设

1. 调度系统启动时，**N 张卡上各启动并常驻一个 vLLM 副本**，直到整次实验结束；不按任务反复冷启引擎。
2. **一个任务 ↔ 一次 Helium（或 Helium_new）实例**：任务开始时启动该实例，跑完关闭/释放；**不同任务是不同实例**，不是全局共用一个 Helium 进程。
3. 任务一旦绑定若干张卡（若干 vLLM），**独占跑完**，中途不抢占、不中途加卡/减卡。
4. 多任务可 **并行**：分别占用不相交的卡集合（例如 4 卡空闲时，一个 debate 占 3 卡，同时一个 iterative 占剩 1 卡）。
5. 计时（两类，均需记录）：
   - **execute 时间**：与现有 ref 脚本一致，即 `server.start()` 之后的纯执行耗时（不含 vLLM 冷启动、不含排队等卡）。  
     聚合指标：**Σ `execute_seconds`**（所有任务 execute 之和）。
   - **段清队时间 `clearance_seconds`**：**本时段最后一个（属于本时段的）任务的结束时刻 − 本时段开始时刻**。  
     归属按「本时段到达/计入本时段的那批任务」计算，**不是**「全局队列清空」——多段时队列可能仍有下段任务或上段残留，不能用队列空当终点；某任务的结束墙钟可以落在后续时段内，但仍计入其归属时段的 clearance。  
     反映调度是否更快消化本波；忙时全一卡并行、闲时分卡等策略主要作用于此。
   - **不用全局墙钟 makespan** 做主指标：多段之间常有「活干完了、下一批还没到」的空窗，会稀释对比；清队按 **时段任务集合** 计算，不把无关空窗算进去。
6. 对照与实验 **同一批任务、同一到达序列**，卡数 N 相同（公平，不对多卡任务做时间加权）。

## 4. 对照组 vs 实验组

### 4.1 对照组（不能分卡 → 几乎无调度）

- 使用 **原版 Helium**：**整图单任务、单卡**。
- 行为：看队列与当前空卡；有空卡则取队头（或按简单规则），启动一个 **只绑 1 个 vLLM** 的 Helium，跑完释放。
- 最多可同时跑 N 个任务（每卡一个）。
- **不存在「分几张卡」的决策**；策略可退化成恒等：`k = 1`。

### 4.2 实验组（可分卡 → 需要调度策略）

- 使用 **Helium_new**：**整图单任务、可变卡数**（同一图实例占用 k 个常驻 vLLM，图内放置由 helium_new 负责，如 spread 等；本课题主故事在 **k 的选择**）。
- 轮到需要安排时，由 **调度策略** 根据队列、标签、空卡情况决定本任务（或当前波次）用几张卡、绑哪些 replica。
- 卡数受查表上限约束，并与空闲数结合（见策略接口与默认策略）。
- 跑完释放占用的卡，供后续任务使用。

### 4.3 差异一句话

| | 对照 | 实验 |
|--|------|------|
| 引擎图系统 | Helium | Helium_new |
| 每任务卡数 | 固定 1 | 策略决定，∈ `[1, min(空闲, 表[标签])]`（默认策略下） |
| 调度 | 有空卡开单卡任务即可 | 必须决策是否分卡、分几张 |

## 5. 在线到达与队列（按时间段成批到达）

**不是**任务一个一个稀疏到达，而是：

- 时间被分成若干 **时间段**（例如每段约 100s，具体长度后定）；
- **每个时间段开头**，一次性到达 **若干个任务**（个数与标签组合可配置/生成），进入队列；
- 段内不再持续「滴答式」单个到达（除非后序改协议）；段末若任务已跑完而下一段尚未开始，会出现空窗——这也是主指标不用 makespan 的原因之一。

每条入队任务已带齐：**场景标签**（给调度看）+ **编译图** + **提示词等运行输入**（给 Helium / Helium_new 跑）。

调度节奏：

- 每段开头：新到的一批入队（可与上一段未完成的任务一起构成当前队列）；
- 有空卡时，把 **当前队列 + 卡状态 + 标签** 交给策略，得到安排并启动；任务跑完释卡后再调度，直到本段相关队列清空或下一段时间段开始（边界细节实现时再钉死）。

忙/闲的精细定义（例如本段队列很长 vs 段末只剩尾巴）**留待后续**；直觉上：一段开头刚涌入很多任务时偏「忙」，不宜把卡都堆给少数任务；段末或队列变短时偏「闲」，更值得按表给单任务更多卡。是否写入策略由接口后的实现决定。

## 6. 调度策略接口（可插拔）

策略与运行时分离，便于替换算法、验证「逻辑上是否有效」。

### 6.1 输入（逻辑上）

- 当前任务队列（本段新到 + 可能的上段残留；顺序；每项含标签，以及图/提示词等运行载荷的句柄）；
- 当前卡状态（哪些 replica 空闲/被哪次运行占用）；
- 可选：场景最优卡数表 `表[标签] → k_max`；
- 可选：时间段上下文（第几段、本段已到任务数等）及其它忙闲参数。

### 6.2 输出（逻辑上）

- **对当前队列的安排**：启动哪些任务、各占用几张卡、绑哪些 vLLM；  
  默认最简实现可每次只安排 **队头一个任务**（有空卡则按降级规则开），后续可换成「一段开头一次性排出多任务占卡方案」。

### 6.3 运行时职责（非策略）

- 按策略输出启动 Helium / Helium_new；
- 维护卡占用与释放；
- 记录每个任务的 execute 时间并求和；
- 不把某一具体分卡公式写死进运行时。

### 6.4 已定的默认策略倾向（最简单，可替换）

> 本小节保留最初的 MVP 方案。后续新增候选 `ParallelReserveStrategy` 的完整规则、参数来源和等待优先级见 [parallel_reserve_strategy.md](parallel_reserve_strategy.md)。

- **降级占用**：表中的 k 是 **上限，不是必须占满**。  
  示意：`实际卡数 = min(当前空闲卡数, 表[标签])`，且至少空闲 1 张才启动队头。  
- **不空等**凑齐表上的「最优卡数」；  
- **不跳过队头**（暂不做更复杂的越过/重排）。  
- 对照策略：恒 `实际卡数 = 1`（有空卡则开）。

示例（与口头约定一致）：

- 空闲 4 卡，队头 debate，表上 debate≤3 → 开 3 卡 Helium_new 跑完该 debate；
- 仍空闲 1 卡，下一队头 iterative，表上 iterative≤1 → 开 1 卡跑该 iterative。

## 7. 指标与评价

双指标（对照 vs 实验，同一任务集、同一到达）：

| 指标 | 含义 | 主要回答 |
|------|------|----------|
| **Σ `execute_seconds`** | 各任务纯执行时间之和（不含等卡） | 分卡 / Helium_new 是否真缩短执行 |
| **`clearance_seconds`** | 本时段最后一任务结束 − 本时段开始（按本时段任务集，非队列清空） | 调度是否更快清完这波 |

- 结果文件除每任务 `execute_seconds` 外，应记录每任务相对到达的 `wall_start` / `wall_end`，以及整段 `clearance_seconds`。
- 单次运行、不同数据之间存在误差与差异，调度结果不一定数值最优；**以策略逻辑是否按设计生效、对比是否符合预期方向为主**。
- 查表来自单场景扫卡实验（如 debate 最优 3、parallel 最优 4 等），实验组 **不超过** 表值。

## 8. 与现有代码/实验的关系（背景）

已有 `benchmark/newResearch` 下 ref 脚本用于 **单任务、固定卡数** 测 execute，并观察：

- iterative：串行链，多卡难加速，分卡易丢同引擎 prefix cache；
- debate：图较宽可并行，但 naive 分卡可能拆散同问多 agent 的公共前缀，卡数并非越多越好；
- parallel：高并行、高负载时分卡更有动机（具体最优 k 由实验填表）。

Helium_new 侧已有 intra-graph placement（如 `spread`）等；本课题调度大纲关注 **任务级 k 与队列安排**，图内放置可作为既有机制沿用，不在本大纲展开实现细节。

## 9. 实现原则（后续）

1. **先不追求一次做完**；按模块推进：大纲 → 策略接口 → 最简运行时环 → 接三类图/自造数据 → 对照与实验跑通 → 再换策略。
2. 策略必须是 **接口**；默认实现可换。
3. 想法可随实验修订（忙闲定义、到达过程、是否允许跳过队头等）；修订时更新本文档。

### 9.1 代码落点（实验组 MVP）

路径：`benchmark/repo/`（包名 `repo`）。核心副本：`src/helium2`、`src/helium_new2`（由 helium / helium_new 拷贝，import 已改写）。

| 模块 | 职责 |
|------|------|
| `config.py` | `DEVICES` / `MODEL` / `K_MAX_TABLE` / `RESULT_PATH` |
| `pool.py` | 常驻 vLLM OpenAI HTTP 池；`acquire_replicas` / `release` |
| `dataset.py` | 先生成内存任务：`label` + `CompiledGraph`（helium2/helium_new2 共用） |
| `strategy.py` | 读队列标签 → `Assignment`/`SchedulePlan`（MVP 恒 k=1，结构齐全） |
| `runner.py` | `flavor=helium2\|helium_new2` + `vllm-openai`；实验默认 new2 |
| `scheduler.py` | 数据集 → 启池 → 有空卡则 plan 并并行启动 → 完成释卡再调度 → 写结果 |
| `__main__.py` | `python -m repo` / `--dry-run`（只出计划、不起引擎） |

流水线：`build_fixed_dataset` → 有空卡反复 `strategy.plan` → 并行 `acquire` + `run_task` → 释卡再调度 → `results/*.txt`（每任务 k/devices/execute/wall + Σ execute + clearance）。  
对照组可把 `flavor="helium2"`；策略后续可换成 `min(free, k_max)` 降级。

## 10. 术语速查

| 术语 | 含义 |
|------|------|
| 整图单任务 | 一次请求执行一张（已编译）agent 计算图 |
| 分卡 | 同一任务占用 k>1 个 vLLM/GPU |
| 查表 k_max | 该场景单任务实验得到的推荐卡数上限 |
| execute 时间 | server 就绪后纯执行阶段耗时（不含等卡） |
| Σ execute | 各任务 execute 之和；与 clearance 并列记录 |
| clearance / 段清队时间 | 本时段最后一任务结束 − 本时段开始；按本时段任务集，非全局队列清空 |
| 降级 | 空闲不足 k_max 时用更少卡启动，不等待 |
| 时间段成批到达 | 每个时间段开头一次到达多个任务入队，而非逐个到达 |
| 任务三件套 | 到达即带齐：标签（调度用）+ 图 + 提示词等（运行用） |

## 11. 当前已拍板 / 仍开放

**已拍板**

- N 卡常驻 vLLM；任务级 Helium 实例；占卡跑完释放；可多任务并行占不同卡。
- 对照单卡 Helium；实验 Helium_new 可变 k。
- 标签已知；三类场景角色如上；表为单场景最优上限。
- 指标：**Σ execute** 与 **段清队时间 `clearance_seconds`** 均记录、均对比；不用跨段全局 makespan。同任务集公平对比。
- 策略可插拔；默认降级、不空等、不跳队头；有空卡且队列非空则调度，多任务可并行占不相交卡。
- **到达模型：按时间段开头成批到达若干任务**（不是一个一个来）。

**仍开放（后序发现再定）**

- 忙/闲的精确定义是否进入策略；
- 时间段长度、每段到达个数与标签配比的具体生成方式；
- 段边界与「上段未完成任务」的衔接细节；
- 策略输出是否在段开头一次安排多个任务；
- 图内 placement 与任务级 k 的联合（若需要）；
- 调度用数据集如何从原始数据生成：格式、规模、标签配比与生成脚本（尚未讨论）。
