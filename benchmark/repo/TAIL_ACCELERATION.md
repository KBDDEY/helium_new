# 末尾加速

仅 `helium_new2` 支持。实验组使用 `AdaptiveStrategy`，将策略1～4作为时段起点互斥选择的基础分支；末尾加速是独立的策略5。`helium2` 固定使用全单卡对照策略。两组的引擎、生成、缓存和端口参数沿用已有配置。

## 开关与触发

在 `config.py` 设置 `ENABLE_TAIL_ACCELERATION = True`，或调用：

```python
run_experiment(enable_tail_acceleration=True)
```

开关默认关闭。开启后，只有等待队列为空、有实际空卡，且存在执行端已启动、尚未结束、未达到上限的 `parallel` 任务时，才尝试追加。等待队列中的 D、I 也必须全部派发后才进入末尾阶段。

按 P 的实际执行开始时间从晚到早，最多将各 P 补到 `K_WISH_TABLE["parallel"]`，不再继续向 `k_max` 追加。实际追加目标为 `min(k_wish, k_max, 总卡数)`。有几张空卡就使用几张，不攒卡。已达到或超过目标的 P 保持已有分配，不再追加；初始分卡规则保持不变。任务结束时归还初始和追加的全部卡。

## 执行边界

保留原有任务图、逻辑 worker、结果引用以及缓存感知调度生成的调用顺序。`helium_new2` 的请求发送扩展只为尚未发出的请求选择已授权的新增引擎。原始引擎保留分配偏好，新增引擎用于分担请求负载；其他初始 worker 的引擎仍属于原 worker。

新卡不自动拥有原卡的前缀缓存。本版没有实现扩卡后的全量物理缓存重规划，也没有更改缓存功能或请求并发参数。已经进入旧 vLLM 的请求继续在旧引擎执行。因此，扩卡获准不等于一定接到了工作，更不等于一定缩短清队时间。

共享状态在执行进程池首次 fork 前建立，新增授权直接对实际 HTTP 发送进程可见。运行期不会再次启动 vLLM 服务。仅当末尾仍有空卡时，父调度循环以短超时检查执行端状态，避免一直等完整任务结束才发现可扩卡机会。

## 服务器验证

为了单独比较末尾加速，实验组保持同一任务队列、同一 `AdaptiveStrategy` 和运行配置，只切换此开关。关闭时仍完整保留策略1～4的自动选择，开启时叠加末尾扩卡。策略4是自适应策略内部的自动回退分支；全单卡对照实验由 `helium2` 承担。

报告新增：

- `tail_summary`：初始卡数与最终持卡数；原 `k` 字段为最终持卡数。
- `card_allocation`：初始分配及每次追加的时刻、卡集合。
- `engine_requests`：实际发送端选中每张授权卡的逻辑请求次数，HTTP 内部重试不重复计数。新增卡计数为零说明这次授权未被后续请求使用；该计数不代表成功完成次数。

先结合新增卡的请求计数和执行日志确认实际使用，再比较 `clearance_seconds`。任务关闭失败统一向上传播，无论是否启用末尾加速。扩卡任务返池前封闭后续请求入口，并检查在途计数，避免旧执行端访问已重新分配的卡。

本地仅做静态代码检查；真实运行与多进程/GPU验证需在服务器完成。新增的 `test_tail_acceleration.py` 可在服务器运行，覆盖队列准入、k_wish 上限、实际开始时间优先、拒绝回滚、共享授权及收尾保护，不启动 vLLM 服务。
